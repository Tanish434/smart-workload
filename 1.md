
# Smart Team Workload Management — Frontend-only build task list

No backend. No API calls. All data lives in a client-side Zustand store, seeded once from a
mock data file. Every user action (filter, create task, mark unavailable, reassign) updates
real in-memory state — nothing is a stub or a dead button. State resets on page refresh since
there's no persistence layer; that's expected for a prototype. (If you later want it to survive
refresh, add Zustand's `persist` middleware — one line, optional.)

Stack: Next.js 14 (App Router, TypeScript) · Tailwind CSS · Zustand

Each task below is self-contained: it names the exact file, what data/types/store functions it
touches, exactly what it must do, what it links to, and how to know it's done. Do them in order —
later tasks depend on earlier ones being in place.

## Phase 0 — Foundations

**T0.1 — Types**

- File: `types/member.ts`, `types/task.ts`
- Does: define
  ```ts
  interface Member {
    id: string; name: string; role: string; skills: string[];
    availability: "available" | "busy" | "unavailable";
    capacityHoursPerWeek: number;
  }
  interface Task {
    id: string; title: string; description: string; requiredSkill: string;
    priority: "low" | "medium" | "high"; deadline: string; // ISO date
    status: "todo" | "in_progress" | "done";
    estimatedHours: number; assignedTo: string | null; // Member.id
  }
  ```
- Done when: both files export their interface, no other file needs edited types.

**T0.2 — Constants**

- File: `lib/constants.ts`
- Does: export
  - `OVERLOAD_THRESHOLD = 100` (workload % at/above this = overloaded)
  - `AT_RISK_THRESHOLD = 85` (workload % at/above this but below overload = "at risk")
  - `DEADLINE_HIGH_RISK_DAYS = 2`, `DEADLINE_MEDIUM_RISK_DAYS = 5`
  - `SKILL_OPTIONS = string[]` (fixed list of ~8 skills used across seed data and the task form, e.g. `["Design","Frontend","Backend","QA","Copywriting","DevOps","Research","Video Editing"]`)
- Done when: no magic numbers/strings for thresholds exist anywhere else in the codebase — everything imports from here.

**T0.3 — Seed data**

- File: `data/seed.ts`
- Uses: `Member`, `Task` types, `SKILL_OPTIONS`
- Does: export `seedMembers: Member[]` (8-10 members, varied skills/availability/capacity) and `seedTasks: Task[]` (18-20 tasks, spread across all statuses/priorities, deadlines ranging from overdue to a month out, some assigned to the same member to force overload, at least 2 with `assignedTo: null`)
- Done when: at least 2 members end up overloaded and at least 3 tasks fall in the high-risk deadline window purely from this seed data — this is what makes the demo look alive on first load.

## Phase 1 — Pure logic (no UI, no store — just functions)

**T1.1 — Workload math**

- File: `lib/workload.ts`
- Uses: `Member`, `Task`, `OVERLOAD_THRESHOLD`, `AT_RISK_THRESHOLD`
- Exports:
  - `getMemberActiveTasks(memberId, tasks): Task[]` — tasks assigned to member where `status !== "done"`
  - `calculateWorkloadPercent(memberId, tasks, members): number` — `sum(estimatedHours of active tasks) / member.capacityHoursPerWeek * 100`, rounded
  - `getWorkloadStatus(percent): "normal" | "at_risk" | "overloaded"` — thresholds from constants
- Links to: every widget/page that shows a workload bar or overload flag calls these — never recompute this math inline anywhere else.
- Done when: calling `calculateWorkloadPercent` on seed data returns different values per member and at least 2 return `"overloaded"`.

**T1.2 — Deadline risk**

- File: `lib/deadlineRisk.ts`
- Uses: `Task`, `getWorkloadStatus`, constants
- Exports: `getDeadlineRisk(task, assigneeWorkloadStatus): "low" | "medium" | "high"` — based on days-until-deadline, escalated one level if `assigneeWorkloadStatus === "overloaded"`, forced `"high"` if deadline is in the past and status isn't `"done"`.
- Done when: an overdue undone task always returns `"high"` regardless of other inputs.

**T1.3 — Suggestion engine**

- File: `lib/suggestEngine.ts`
- Uses: `Member`, `Task`, `calculateWorkloadPercent`
- Exports: `getSuggestedMembers(draftTask: Pick<Task,"requiredSkill"|"priority">, members, tasks): {member: Member; score: number; reasons: string[]}[]`
  - Excludes members with `availability === "unavailable"`
  - Score: `+40` if `skills.includes(requiredSkill)`, `+30 * (1 - workload%/100)` (clamp at 0), `+20` if `availability === "available"`
  - `reasons` is a short string array like `["Has required skill", "Currently available", "Low current workload"]` used to render badges in the UI
  - Sorted descending by score
- Done when: passing a draft task with a rare skill returns members with that skill ranked above members without it, even if the latter have more free capacity.

**T1.4 — Alerts engine**

- File: `lib/alertsEngine.ts`
- Uses: `getWorkloadStatus`, `getDeadlineRisk`, `Member`, `Task`
- Exports: `deriveAlerts(members, tasks): { overloadedMembers: Member[]; deadlineRisks: {task: Task; risk: string}[]; rebalanceSuggestions: {task: Task; from: Member; to: Member}[] }`
  - `rebalanceSuggestions`: for each task assigned to an overloaded member, find the top-scoring alternative from `getSuggestedMembers` who is not overloaded — propose that swap.
- Done when: on seed data this returns at least 1 non-empty rebalance suggestion.

## Phase 2 — Store (state layer, replaces the backend entirely)

**T2.1 — Store shape + selectors**

- File: `store/useWorkloadStore.ts`
- Uses: `seedMembers`, `seedTasks`, all of Phase 1
- Does: Zustand store with state `{ members: Member[]; tasks: Task[] }` initialized from seed, plus selectors as plain functions/hooks:
  - `useMembers()` → members with computed `workloadPercent` and `workloadStatus` attached
  - `useMemberById(id)` → single member (as above) + their tasks
  - `useTasks(filters?: {status?, priority?, assignedTo?})` → filtered tasks, each with `deadlineRisk` attached
  - `useTaskById(id)`
  - `useAlerts()` → calls `deriveAlerts`
  - `useDashboardSummary()` → `{ totalMembers, activeTasks, overloadedCount, upcomingDeadlineCount }`
- Done when: every page can get everything it needs from one of these hooks — no page reaches into `data/seed.ts` directly.

**T2.2 — Task actions**

- File: same store file
- Does: `createTask(data: Omit<Task,"id">)`, `updateTask(id, updates: Partial<Task>)`, `deleteTask(id)` — all mutate `tasks` array immutably and trigger re-render everywhere via Zustand.
- Done when: calling `createTask` from a component immediately shows the new task on `/tasks` without a refresh.

**T2.3 — Member availability action**

- File: same store file
- Does: `updateMemberAvailability(id, status): Task[]` — updates the member, and **returns the list of that member's currently active tasks** so the calling component knows what needs reassigning.
- Links to: this return value drives the mark-unavailable flow in T6.7.
- Done when: setting a member to `"unavailable"` immediately drops their workload bar contribution from all overload calculations (since active-task lookups now see them as unavailable, downstream UI should stop suggesting them).

**T2.4 — Reassign action**

- File: same store file
- Does: `reassignTask(taskId, newAssigneeId, reason)` — sets `task.assignedTo = newAssigneeId`, no other side effects needed since workload is always derived live from `tasks`.
- Done when: after calling this, both the old and new assignee's workload % update correctly everywhere (dashboard, team list, alerts) with no manual recompute step needed anywhere else.

**T3.6 — Toast.tsx** — bottom-corner (desktop) / bottom-center (mobile) confirmation toast, auto-dismiss after 3s. Fired after: task created, task reassigned, member availability changed.

## Phase 7 — Tasks (`/tasks`, `/tasks/new`, `/tasks/[taskId]`)

**T7.1 — DeadlineRiskTag.tsx** — thin wrapper on `Badge variant="risk"`, takes a `Task` and computes risk via `getDeadlineRisk` + the assignee's workload status pulled from `useMemberById`.

**T7.2 — TaskCard.tsx** — title, assignee name+avatar (or "Unassigned"), deadline date, `Badge variant="priority"`, `DeadlineRiskTag`. Whole card links to `/tasks/[id]`.

**T7.3 — TaskFilterBar.tsx** — status/priority/assignee dropdowns, filters `useTasks()` client-side.

**T7.4 — TaskBoard.tsx** — 3 columns (`todo`, `in_progress`, `done`), each a list of `TaskCard`. On mobile: tabs to switch between the 3 columns instead of side-by-side (don't shrink columns to unreadable width).

**T7.5 — app/(dashboard)/tasks/page.tsx** — `TaskFilterBar` + `TaskBoard` + "Add task" `Button` → `/tasks/new`.

**T7.6 — TaskForm.tsx** — controlled inputs: title (text, required), description (textarea), requiredSkill (select from `SKILL_OPTIONS`, required), priority (select), deadline (date input, required, must be today or later), estimatedHours (number, required, >0). Inline validation errors shown under each field on submit attempt; submit button disabled until required fields are valid. Emits the draft task object up on every change (for T7.7 to consume live) and on submit.

**T7.7 — SuggestedMembersPanel.tsx**

- Uses: `getSuggestedMembers` from `lib/suggestEngine.ts`
- Props: current draft task (`requiredSkill`, `priority`) from `TaskForm`
- Behavior: recalculates and re-renders the ranked list on every relevant form field change (no submit needed) — this is the "live suggestion" feature. Each row shows member name, score-derived rank, and the `reasons` badges from T1.3. Clicking a suggested member pre-fills `assignedTo` in the form.

**T7.8 — app/(dashboard)/tasks/new/page.tsx** — `TaskForm` + `SuggestedMembersPanel` side-by-side on desktop, stacked (form first, suggestions below) on mobile. On valid submit: calls `createTask`, fires `Toast`, `router.push("/tasks")`.

**T7.9 — app/(dashboard)/tasks/[taskId]/page.tsx** — read/edit view of one task using `TaskForm` pre-filled, a status `Badge`/dropdown to move it through `todo → in_progress → done`, and a "Reassign" `Button` → `/tasks/[id]/reassign`. Saves via `updateTask`.

## Phase 9 — Reassignment flow

**T9.1 — ReassignPanel.tsx**

- Uses: `useTaskById`, `getSuggestedMembers`, `reassignTask`
- Behavior: shows current assignee card (or "Unassigned"), ranked suggestion list (same rendering as T7.7), a reason radio group (`Member unavailable | High-priority swap | Manual`), and a Confirm `Button` disabled until a member is selected. On confirm: calls `reassignTask(taskId, selectedId, reason)`, fires `Toast`.

**T9.2 — app/(dashboard)/tasks/[taskId]/reassign/page.tsx**

- Wraps `ReassignPanel` in `Modal` (or full page on mobile since Modal already goes full-screen there)
- Reads the optional `queue` query param (see T6.7). After a successful reassign: if `queue` has remaining task IDs, `router.push` to the reassign page for the next one; if empty, `router.push` back to the referring page (member detail or tasks list).
- Done when: the mark-unavailable → reassign chain from T6.7 can walk through every affected task without ever losing track of which ones are left.

## Definition of done for the whole prototype

All six required concepts from the brief are interactive, not static:

1. Team overview filters/sorts live members — T6.3/T6.5
2. Workload is computed live from real task data everywhere it's shown — T1.1/T2.1
3. Overloaded members are auto-flagged, not hardcoded — T1.1/T1.4/T8.1
4. Deadline risk auto-escalates near due dates and for overloaded assignees — T1.2/T5.3/T8.2
5. New-task suggestions re-rank live as the form changes — T7.7
6. Reassignment works both manually and as a triggered flow from unavailability — T6.7/T9.1/T9.2
